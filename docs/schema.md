# Schema

## What data does the system store?

The application uses MongoDB with Mongoose. The current schema contains five main collections:

- Users
- Grant Applications
- Assignments
- Reviews
- Conflicts
- Conflicts
- Application History
- Alerts

MongoDB automatically provides an `_id` for each document. Mongoose timestamps are also enabled on all current models, adding `createdAt` and `updatedAt`.

---

## User

The `User` collection stores the accounts that can access the system.

### Fields

- `_id` — MongoDB ObjectId, automatically generated primary identifier
- `name` — String, required, trimmed
- `email` — String, required, unique, converted to lowercase and trimmed
- `password` — String, required, stored as a bcrypt hash
- `role` — String, required, either `PROGRAM_OFFICER` or `REVIEWER`
- `createdAt` — Date, automatically generated by Mongoose
- `updatedAt` — Date, automatically updated by Mongoose

### Constraints

The database enforces a unique constraint on `email` so that two users cannot have the same email address.

The `role` field is limited to the two roles currently supported by the system:

- `PROGRAM_OFFICER`
- `REVIEWER`

Passwords are not stored in plain text. A Mongoose pre-save hook hashes the password using bcrypt before it is saved.

---

## Grant Application

The `GrantApplication` collection stores grant applications managed by Program Officers.

### Fields

- `_id` — MongoDB ObjectId, automatically generated primary identifier
- `applicantOrganizationName` — String, required, trimmed
- `contactEmail` — String, required, converted to lowercase and trimmed
- `fundingRound` — String, required, trimmed
- `amountRequested` — Decimal128, required
- `submissionDate` — Date, required
- `owner` — ObjectId referencing a `User`, required
- `status` — String representing the application's current lifecycle status
- `isArchived` — Boolean, defaults to `false`
- `archivedAt` — Date, defaults to `null`
- `createdAt` — Date, automatically generated by Mongoose
- `updatedAt` — Date, automatically updated by Mongoose

### Status values

The `status` field is restricted to:

- `SUBMITTED`
- `ASSIGNED`
- `UNDER_REVIEW`
- `DECIDED`

The default status for a newly created application is `SUBMITTED`.

### Exact decimal amounts

`amountRequested` uses MongoDB's `Decimal128` type instead of a JavaScript floating-point number.

This was chosen because grant amounts represent exact financial values, and floating-point values can introduce precision issues.

### Archive behaviour

Applications are not deleted when archived.

Instead:

- `isArchived` is set to `true`
- `archivedAt` stores the time the application was archived

This allows an application to be hidden from normal views while keeping its data available for restoration.

## Assignment

The `Assignment` collection represents the relationship between grant applications and reviewers.

### Fields

- `_id` — MongoDB ObjectId, automatically generated primary identifier
- `application` — ObjectId referencing a `GrantApplication`, required
- `reviewer` — ObjectId referencing a `User`, required
- `dueDate` — Date, required
- `isActive` — Boolean, defaults to `true`
- `createdAt` — Date, automatically generated by Mongoose
- `updatedAt` — Date, automatically updated by Mongoose

### Constraints

A compound unique index is defined on:

* `application`
* `reviewer`

This prevents the same reviewer from being assigned to the same application more than once.

When a reviewer declares a conflict of interest, their active assignment is deactivated. The conflict record remains stored separately, so the Program Officer cannot assign the same reviewer to that application again.


---

## Review

The `Review` collection stores a review written by a reviewer for a grant application.

### Fields

- `_id` — MongoDB ObjectId, automatically generated primary identifier
- `application` — ObjectId referencing a `GrantApplication`, required
- `reviewer` — ObjectId referencing a `User`, required
- `impactScore` — Number from 1 to 5, optional while a review is in `DRAFT`; required when a review is completed
- `feasibilityScore` — Number from 1 to 5, optional while a review is in `DRAFT`; required when a review is completed
- `budgetJustificationScore` — Number from 1 to 5, optional while a review is in `DRAFT`; required when a review is completed
- `comments` — String, optional while a review is in `DRAFT`; required when a review is completed
- `status` — String, either `DRAFT` or `COMPLETED`
- `createdAt` — Date, automatically generated by Mongoose
- `updatedAt` — Date, automatically updated by Mongoose

### Score constraints

Each scoring criterion is limited to a minimum value of `1` and a maximum value of `5`.

The three fixed criteria are:

- Impact
- Feasibility
- Budget Justification

### Review status

A review can currently have one of two states:

- `DRAFT`
- `COMPLETED`

The default state is `DRAFT`.

### Constraints

A compound unique index is defined on:

- `application`
- `reviewer`

This ensures that one reviewer can have only one review record for a particular application.

---

## Conflict

The `Conflict` collection stores declared conflicts of interest.

### Fields

- `_id` — MongoDB ObjectId, automatically generated primary identifier
- `application` — ObjectId referencing a `GrantApplication`, required
- `reviewer` — ObjectId referencing a `User`, required
- `reason` — String, required and trimmed
- `createdAt` — Date, automatically generated by Mongoose
- `updatedAt` — Date, automatically updated by Mongoose

### Constraints

A compound unique index is defined on:

- `application`
- `reviewer`

This ensures that a reviewer can declare only one conflict record for a particular application.

## Relationships

The system uses ObjectId references to represent relationships between documents.

### User to Grant Application

One Program Officer can own many grant applications.

Each grant application has one owning Program Officer.

```text
User
  1
  │
  └──────< GrantApplication
```

### Grant Application to Assignment

One grant application can have multiple reviewer assignments.

Each assignment belongs to one grant application.

```text
GrantApplication
       1
       │
       └──────< Assignment
```

### User to Assignment

One reviewer can have multiple assignments over time.

Each assignment belongs to one reviewer.

```text
User
  1
  │
  └──────< Assignment
```

Together, the `Assignment` collection models a many-to-many relationship between reviewers and grant applications.

```text
User (Reviewer)
       │
       │
       ├──────< Assignment >──────┤
                                   │
                           GrantApplication
```

### Grant Application to Review

One grant application can have reviews from multiple reviewers.

Each review belongs to one grant application.

### User to Review

One reviewer can create reviews for multiple applications.

Each review belongs to one reviewer.

The compound unique index prevents duplicate reviews from the same reviewer for the same application.

### Grant Application to Conflict

One grant application can have conflicts declared by multiple reviewers.

Each conflict belongs to one application and one reviewer.

The compound unique index prevents duplicate conflict declarations for the same reviewer and application pair.

## Which constraints live in the database versus the application?

### Database and schema-level constraints

The Mongoose schemas and MongoDB indexes enforce structural constraints such as:

- Required fields
- Unique user emails
- Valid role values
- Valid application status values
- Review score ranges from 1 to 5
- Unique reviewer/application assignments
- Unique reviewer/application reviews
- Unique reviewer/application conflicts

These constraints protect the database from invalid document structures and duplicate relationship records.

### Application-level constraints

More complex workflow rules belong in controllers and business logic because they depend on checking related records and the current state of the system.

Examples include:

- Only Program Officers can create, edit, archive, restore, or manage applications
- Reviewers can only access applications assigned to them
- Application status transitions must follow the defined lifecycle
- An application cannot be decided until enough completed reviews exist
- A reviewer with a conflict cannot be assigned to that application
- A reviewer cannot exceed the active assignment limit
- Completed reviews cannot be edited
- Completed reviewer assignments cannot be removed

Additional application-level workflow constraints include:

* A reviewer must have an active assignment before creating or completing a review.
* A reviewer who has declared a conflict cannot review the application.
* A reviewer who has declared a conflict cannot be assigned to the same application again.
* Declaring a conflict deactivates the reviewer's active assignment.
* An application requires at least one reviewer assignment before moving to `ASSIGNED`.
* An application requires at least three completed reviews before moving to `DECIDED`.
* A reviewer can have a maximum of five active assignments.

These rules require application logic because they involve multiple documents or depend on the current workflow state.

## What was deliberately denormalised?

The current schema keeps the main relationships as separate collections rather than embedding assignments, reviews, and conflicts directly inside the Grant Application document.

This avoids creating very large application documents and allows assignments, reviews, and conflicts to be queried independently.

Some data is intentionally referenced instead of copied. For example:

- Applications reference their owner
- Assignments reference an application and reviewer
- Reviews reference an application and reviewer
- Conflicts reference an application and reviewer

User names and other referenced information can be populated when needed.

The current schema does not deliberately duplicate aggregate values such as review counts or average scores on the application document. These values can be calculated from related records when required.

## What would break first at 100x the data?

At a much larger scale, the first areas likely to need attention would be query performance and aggregation work.

### Application listing

Searching, filtering, sorting, and paginating applications would need carefully designed database indexes, especially for fields such as:

- `isArchived`
- `status`
- `fundingRound`
- `owner`
- `submissionDate`

Text search using regular expressions may become expensive as the number of applications grows. A dedicated text index or search service could eventually be more appropriate.

### Relationship queries

Assignment, review, and conflict lookups would become more frequent as the number of users and applications increases.

Additional indexes may be needed for common queries such as:

- Active assignments by reviewer
- Assignments by application
- Completed reviews by application
- Conflicts by application and reviewer

### Dashboard calculations

Dashboard statistics and charts could become expensive if they repeatedly calculate totals from the full application collection.

At a larger scale, precomputed aggregates, background jobs, or caching could be introduced for frequently requested statistics.

### Pagination

The current approach uses `skip` and `limit`. At very large page counts, `skip` becomes less efficient.

Cursor-based pagination could be introduced if the dataset grows significantly.

The current schema is appropriate for the expected size of the take-home project, while keeping the relationships separate enough to allow future scaling improvements.
